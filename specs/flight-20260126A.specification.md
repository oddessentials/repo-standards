# Flight 20260126A — Unified Standards Workspace Edition

> **Status:** Specification
> **Type:** Feature Implementation
> **Scope:** @oddessentials/repo-standards
> **Target:** Constitution Compliance

---

## Executive Summary

This specification defines the implementation of **Flight 20260126A**, which closes the gap between the current repo-standards implementation (a configuration distribution library) and the requirements defined in the Agent Constitution (`docs/agents/CONSTITUTION.md`).

Upon completion, repo-standards will evolve from a **standards distribution package** into an **orchestration platform** that enables downstream consumers (odd-standards-conductor, odd-issue-manager) to implement enterprise-grade compliance automation.

---

## Problem Statement

### Current State

repo-standards currently provides:

- Standards distribution (JSON config files for 5 stacks)
- Standards loading API (`getStandards()`, `getSchema()`)
- CLI wrapper for dumping standards JSON
- Self-compliance with v7 standards

### Required State (Constitution)

The Agent Constitution requires:

- **4 operational commands**: `apply`, `verify`, `doctor`, `migrate`
- **7 schema definitions**: VerifyResult, Finding, SessionLog, GateStatus, VictoryDeclaration, HumanResponse, InputManifest
- **7 operational systems**: Verification, Remediation Routing, Session Management, Audit Logging, Quality Gates, Victory Gates, Human-in-Loop
- **16 invariant enforcement mechanisms**

### Gap

The constitution is **aspirational**; the implementation is **foundational**. There is a **100% gap** in operational capabilities.

## Requirements

### Functional Requirements

#### FR-1: Verification System

**FR-1.1** The system MUST implement a `verify` command that evaluates repository compliance against declared standards.

**FR-1.2** The `verify` command MUST produce a `VerifyResult` conforming to schema v1.1.0.

**FR-1.3** The `verify` command MUST be deterministic: same inputs MUST produce same outputs.

**FR-1.4** The `verify` command MUST compute and include `input_hash` for reproducibility verification.

**FR-1.5** The `verify` command MUST classify findings with: severity, remediation_class, risk, estimated_scope.

**FR-1.6** The `verify` command MUST NOT access the network during execution.

#### FR-2: Application System

**FR-2.1** The system MUST implement an `apply` command that stamps repositories with required standards artifacts.

**FR-2.2** The `apply` command MUST be idempotent: running twice produces identical results.

**FR-2.3** The `apply` command MUST produce a structured apply report.

**FR-2.4** The `apply` command MUST respect `.odd/standards.toml` configuration.

#### FR-3: Diagnostic System

**FR-3.1** The system MUST implement a `doctor` command that analyzes findings and proposes remediation strategies.

**FR-3.2** The `doctor` command MUST classify findings by remediation_class: mechanical, ai, human.

**FR-3.3** The `doctor` command MUST provide actionable remediation_hint for each finding.

#### FR-4: Migration System

**FR-4.1** The system MUST implement a `migrate` command that assists with standards version upgrades.

**FR-4.2** The `migrate` command MUST generate migration plans between versions.

**FR-4.3** The `migrate` command MUST identify breaking changes.

#### FR-5: Schema Definitions

**FR-5.1** The system MUST define and export `VerifyResult` interface.

**FR-5.2** The system MUST define and export `Finding` interface with all routing metadata.

**FR-5.3** The system MUST define and export `SessionLog` interface for session management.

**FR-5.4** The system MUST define and export `GateStatus` interface for quality gates.

**FR-5.5** The system MUST define and export `VictoryDeclaration` interface for victory gates.

**FR-5.6** The system MUST define and export `HumanResponse` interface for approval workflows.

**FR-5.7** The system MUST define and export `InputManifest` interface for determinism.

#### FR-6: Session Management

**FR-6.1** The system MUST support session initialization with UUID v4 session IDs.

**FR-6.2** The system MUST track session state through defined phases.

**FR-6.3** The system MUST support session persistence and retrieval.

**FR-6.4** The system MUST support session replay from audit trail.

#### FR-7: Audit Logging

**FR-7.1** The system MUST produce append-only audit logs.

**FR-7.2** Audit logs MUST include: timestamp, correlation_id, action, intent, execution_result, details.

**FR-7.3** Audit logs MUST support sealing at session completion.

**FR-7.4** Audit logs MUST enable complete session reconstruction.

#### FR-8: Quality Gate Framework

**FR-8.1** The system MUST implement all entry gates: EG-01, EG-02, EG-03.

**FR-8.2** The system MUST implement all phase gates: PG-01 through PG-05.

**FR-8.3** The system MUST implement all exit gates: XG-01 through XG-04.

**FR-8.4** The system MUST implement all remediation gates: RSG-01, RSG-02, RSG-03.

**FR-8.5** Gate evaluation MUST collect evidence for each criterion.

#### FR-9: Victory Gate Framework

**FR-9.1** The system MUST implement victory gates: VG-001 through VG-005.

**FR-9.2** The system MUST implement remediation victory gates: VG-R01, VG-R02, VG-R03.

**FR-9.3** Victory declarations MUST verify all requirements before declaration.

#### FR-10: Human-in-Loop Integration

**FR-10.1** The system MUST define notification channels for human escalation.

**FR-10.2** The system MUST support human response capture.

**FR-10.3** The system MUST enforce timeout behavior (default 24h, escalate at 12h).

### Non-Functional Requirements

#### NFR-1: Determinism

**NFR-1.1** All verification operations MUST be deterministic.

**NFR-1.2** `input_hash` MUST be stable across repeated runs with identical inputs.

**NFR-1.3** Network access MUST be prohibited during verification.

#### NFR-2: Performance

**NFR-2.1** `verify` command MUST complete within 60 seconds for repositories under 10,000 files.

**NFR-2.2** `apply` command MUST complete within 30 seconds for typical repositories.

#### NFR-3: Compatibility

**NFR-3.1** All new interfaces MUST be exported from package entry point.

**NFR-3.2** Existing public API (`getStandards`, `getSchema`) MUST remain unchanged.

**NFR-3.3** CLI MUST support new commands alongside existing functionality.

#### NFR-4: Downstream Compatibility

**NFR-4.1** Schema definitions MUST align with odd-standards-conductor constitution expectations.

**NFR-4.2** Schema definitions MUST align with odd-issue-manager constitution expectations.

**NFR-4.3** API MUST be consumable by orchestration systems.

## Constraints

### C-1: Constitutional Constraints

All implementation MUST comply with the 16 invariants defined in `docs/agents/CONSTITUTION.md`:

- 6 ABSOLUTE invariants (zero exceptions)
- 5 ENFORCED invariants (mechanically blocked)
- 5 REQUIRED invariants (compliance mandatory)

### C-2: Backward Compatibility

Existing public API MUST NOT break:

- `getStandards(stackId, ciSystem?)`
- `getSchema()`
- CLI `repo-standards <stack> [ci-system]`

### C-3: No External Runtime Dependencies

Core functionality MUST NOT require:

- Network access
- External databases
- Third-party services

### C-4: Self-Compliance

repo-standards MUST remain compliant with its own v7 standards throughout implementation.

## Out of Scope

The following are explicitly **NOT** in scope for Flight 20260126A:

1. **Remediation Execution** — repo-standards defines verification and routing; execution is conductor's responsibility
2. **Notification Delivery** — repo-standards defines notification schema; delivery is conductor's responsibility
3. **Session Persistence Backend** — repo-standards defines session schema; persistence is consumer's choice
4. **Human Response Collection** — repo-standards defines response schema; collection is conductor's responsibility
5. **AI Agent Integration** — repo-standards provides finding classification; agent invocation is conductor's responsibility
